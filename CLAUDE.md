## Architecture

CatPuzzle is a "one cat per row/column/Region, no adjacent cats" logic puzzle. The codebase is split into two strictly separated layers:

- **`Sources/CatPuzzleCore`** — a pure Swift Package (no UIKit/SwiftUI/SpriteKit/third-party deps) holding the entire rules engine. This boundary is load-bearing: nothing in this target may import a UI framework.
- **`CatPuzzleApp`** — the SwiftUI app: screens, `GameViewModel`, persistence, sound, and gesture handling. UI code never re-implements game rules; it calls into `GameEngine`/`GameViewModel` domain APIs.

### Core domain flow (`Sources/CatPuzzleCore`)

- `Cell` / `CellState` — board coordinate + Region, and the three-state cell value (empty/excluded/cat).
- `Puzzle` — stores the board layout and current player state; `PuzzleValidator` does side-effect-free placement/conflict/solved checks against it.
- `LevelDefinition` — id, size, cat count, max mistakes, Region-ID grid. `BuiltInLevels` is **generated offline** and must not be hand-edited: it ships three ten-level cycles (8×8 → 9×9 → 10×10, each cycle ending on a `hard`-blueprint board), regenerated by `swift run -c release CatPuzzleGenerator --ladder` — see `Docs/LevelLadder.md`. `SampleLevels` holds three hand-authored 6×6 boards, which are a fixed reference set for tests and tooling, not shipped content. `TutorialLevels` holds the single hand-authored 6×6 board that teaches all three rules (`PuzzleRule`) before the ladder starts; it has no given cats, so `PuzzleSolver` certifies it like any ladder level. `TutorialScript` **derives** that board's move-by-move lesson (`TutorialStep`: a `TutorialLesson`, the `TutorialTask` the step waits for, `.guided` vs `.discovery` coaching, and the cells to spotlight) rather than listing it, and returns an empty script for a board that cannot teach in that order — see `Docs/Tutorial.md`. `LevelValidator` checks a definition's internal consistency (dimensions, cat/Region counts, mistake config) without imposing Region connectivity.
- `GameEngine.setState` is the single core domain operation: every cat placement is validated here, and it atomically owns board mutation, mistake tracking, undo history, and restart. `GameEngine.toggleCell` is a convenience adapter over `setState` implementing the MVP cycle `empty → excluded → cat → empty`; UI is free to call `setState` directly for other gesture mappings instead. Setting a cell to its current state is a no-op (no undo entry). An illegal cat placement is rejected, increments mistakes, and does not create undo history. Once the mistake limit is hit, only Restart is allowed.
- `GameState` — read-only snapshot exposed to callers: current puzzle, mistake count, solved/failed flags.
- Two independent solvers exist for different purposes:
  - `PuzzleSolver` — budgeted MRV search with occupancy bitsets, used as the safety net proving a level is mathematically solvable and has a unique solution. `PuzzleSolverReport` includes deterministic statistics; budget exhaustion is `.inconclusive`, never `.none`.
  - `LogicalPuzzleSolver` — models per-cell candidates and emits deterministic, explainable technique events plus the candidate-board snapshot after each event. Supports `.logicOnly` (used for the shipped levels) and bounded `.challenge(maxAssumptionDepth:)` proof-by-contradiction. Any report that required an assumption is classified as `challenge`.
  - `PuzzleDifficultyAnalyzer` turns a `LogicalPuzzleSolver` report into a deterministic score/tier.
- Screenshot import lives here too, because it is deterministic data-in/data-out analysis and has to be testable from `swift test`: `ScreenshotPixels` is a plain RGB buffer (no image framework — the app layer decodes into it), `ScreenshotBoardTranscriber` reads a board's Region layout and drawn marks back out of one, and `ScreenshotLevelImporter` certifies the result with `PuzzleSolver` and reconciles the marks against the unique solution so an imported board is always winnable. The transcriber's thresholds were measured against real screenshots; `Tests/CatPuzzleCoreTests/SyntheticBoardImage.swift` reproduces that geometry so tests need no checked-in images.

### App layer (`CatPuzzleApp`)

- `AppSession` is the top-level `ObservableObject` router: on launch it loads `GameProgress` from `GameProgressStore`, rebuilds a `GameEngine` from any in-progress `SavedGame`, and routes between `.tutorial` / `.playing` / `.readyForNextLevel` / `.allCompleted` (`AppDestination`). It persists progress on every `GameState` change via callbacks from `TutorialViewModel` and `GameViewModel`.
- `GameProgressStore` is a protocol; `UserDefaultsGameProgressStore` is the concrete `UserDefaults`-backed implementation, JSON-encoding `GameProgress` (completed level IDs + active `SavedGame`). Tests must inject a fake/in-memory store — never touch `UserDefaults.standard` directly (see AGENTS.md testing guidance).
- `GameViewModel` wraps a `GameEngine` instance for one active level, publishing `puzzle`, `canUndo`, `isSolved`, `isFailed`, `mistakeCount`, `feedbackMessage`, and `previewStates` (for drag-marking) to SwiftUI. It uses `CellInputCoordinator`, shared with `TutorialViewModel`, to resolve tap and drag gestures without desyncing from `GameEngine`'s undo history.
- The tutorial is offered before anything else and played once ever, tracked by `GameProgress.completedTutorialIDs` — kept apart from `completedLevelIDs` because that set is cleared on every ladder wrap. It is forced into `.challenge` mode so a wrong cat is refused instead of landing and knocking the script off its board; `maxMistakes` is unreachable and `TutorialScreen` omits the mistake counter and Hint button, so it cannot be lost. `TutorialCoach` (app layer) resolves which `TutorialStep` is current by re-reading the board — the first step the board does not satisfy — so restart, resume and a cleared mark all land correctly with no counter to desync. `TutorialViewModel` exposes `step`, `spotlight`, `interactivePositions`, and `nudgedPositions`: guided steps mask the board and restrict input, while discovery steps nudge outstanding cells after inactivity.
- `LevelPresentation` is what the screens read for a level's title and whether it is the tutorial. Generated levels have slug ids, so nothing in a `LevelDefinition` is fit to show a player. Which rule is on screen belongs to the current `TutorialStep`, not to the level.
- `LevelProgression` maps the ordered `BuiltInLevels` list against a set of completed IDs to find the next unfinished level. The ladder is a **loop**: when every level is complete, `nextLevel` returns the first level with `didWrap`, and `AppSession` clears the finished lap. `.allCompleted` is now only reachable with no levels at all. Generated levels have slug ids, so `AppSession` assigns `LevelPresentation.ladder(number:)` using each level's position in the fixture list.
- `ScreenshotPixelDecoder` is the only place in the import path that touches an image framework: it redraws a picked `UIImage` into a `ScreenshotPixels` buffer (normalising orientation, color space, and scale). `ScreenshotImportScreen` (Settings → Play from Screenshot) drives the PhotosUI picker, runs decode + import off the main actor, previews the parsed board, and plays it through the normal `GameScreen`. Imported boards are scratch games — like `PlaytestLabScreen`, they never touch `GameProgress`.
- `BoardView`/`CellView`/`GameScreen` render the puzzle and translate taps/drags into `GameViewModel` calls (drag-to-mark-exclusions, drag-to-clear-exclusions — see DESIGN.md for exact interaction semantics). `PuzzleSound` plays distinct mark/unmark SFX from `CatPuzzleApp/Sounds/`.

### Design reference

`DESIGN.md` defines the semantic color tokens, typography, per-cell-state visuals, and interaction rules (tap/drag/double-tap timing, accessibility requirements) that UI changes must follow — read it before touching `BoardView`, `CellView`, or `GameScreen`.
